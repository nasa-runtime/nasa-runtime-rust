# 应用运维指南

本文说明应用模式进程的日常观测、停机语义和故障排查。业务特有的端口、下游依赖和数据恢复流程
仍由对应项目手册补充。

## 运行状态

应用生命周期按以下方向单向推进：

```text
Bootstrap → Starting → UserHook → Ready → Running → Stopping → Stopped
                                                        └────→ Failed
```

- `Ready` 只在组件启动、业务 Hook 成功、资源封存以及需要的 listener 绑定后提交。
- 任一关键任务在 Running 阶段意外结束会提交失败意图，整个进程进入统一停机。
- 进入 Stopping 后 readiness 先变为 false，再执行摘流、停止 accept、排空任务和反向释放资源。
- `Failed` 是终态，不会再回到 Stopping 或 Running。

## 退出码

| 场景 | 结果 |
| --- | --- |
| 常驻服务首次收到 Ctrl-C 或 SIGTERM，并在预算内清理完成 | `0` |
| 启动失败或关键任务先发生故障 | 非零 |
| 批处理尚未完成时收到信号 | `128 + signal` |
| 批处理业务结果已提交后在清理阶段强退 | `0` |
| Stopping 阶段再次收到终止信号 | 立即退出，按已提交终止意图决定 |

外部监督器应同时记录退出码和停机前的 primary error。清理阶段的后续错误进入 shutdown report，
不会覆盖更早提交的根因。

## 日常检查

对声明框架 Web 组件的服务，优先检查带上下文前缀的 `/readyz` 和 `/healthz`。对自行托管 listener
的应用，检查项目管理面、业务就绪日志和实际端口，不能只判断进程号存在。

一次常规巡检应确认：

- 应用名称、模式和最终配置版本符合部署批次。
- Ready 后的真实监听地址与服务发现注册地址一致。
- 关键任务没有提前退出，后台任务数量没有持续增长。
- 数据库池、缓存客户端、配置监听和服务发现处于各自最后一次成功运行态。
- 配置刷新没有 `ApplyFailed` 或 `RestartRequired` 长时间未处理。
- 日志中没有连接串凭据、访问令牌或原始异常载荷。

## 配置刷新

配置视图把期望快照和每个组件的应用状态放在同一 commit 中发布。运维判断时必须同时查看版本与状态：

- `Applied`：组件已应用该版本。
- `ApplyFailed`：期望配置已更新，但组件仍运行在最后一次成功状态；先处理错误，不要假定运行态已变化。
- `RestartRequired`：字段不能热切，安排滚动重启。
- 未声明组件没有伪造状态；配置段存在时会产生对应告警。

远端配置试图修改 `application.*` 时不会动态改变进程身份、模式、线程数或全局 deadline。首拉阶段的
冲突会拒绝启动，运行期冲突会标记需要重启。

## 停机与超时

正常停机只发送一次 SIGTERM，然后等待进程自行退出。清理顺序遵循已启动动作的严格反序，典型顺序为：

```text
NotReady / 摘流
  → 停止 listener 接收
  → 排空 Web 与用户任务
  → 关闭业务托管资源
  → 关闭数据库、缓存和配置监听
  → 刷新日志并退出
```

所有异步清理共享一个绝对截止时间。超时后运行时会记录未完成阶段并中止可取消任务；任意同步析构、
不让出执行权的代码或无法取消的阻塞工作仍需要部署平台的最终强制终止上限兜底。

## 常见启动故障

| 现象 | 优先检查 |
| --- | --- |
| 找不到主配置 | 进程工作目录、`zcf/application.yml` 是否随产物部署 |
| 无 Web 后进程在 Hook 返回后退出 | `application.mode` 是否显式为 `service` |
| 配置反序列化失败 | 环境键层级、主配置字段类型、旧键与当前键是否并存 |
| 声明组件但启动提示 feature 缺失 | 业务 `Cargo.toml` 是否打开对应门面 feature |
| listener 启动超时 | 地址是否可绑定、端口是否占用、业务就绪屏障是否真正提交 |
| 数据库或缓存失败 | 使用脱敏后的目标主机、端口、模式和超时定位，不打印完整连接串 |
| Ready 后很快退出 | 查看首个 critical task 错误，不能只看最后一条 shutdown warning |
| SIGTERM 后超过预算 | 查找未 join 的任务、长期资源借用、无限流式响应或阻塞析构 |

## 已知边界

- 缓存失效广播在完成可取消、可 join 的受管句柄前，不能计入“所有长任务都已被监督”的结论。
- 进程级 OnceLock 资源只随进程回收，当前不支持同进程反复创建多个完整应用实例。
- 自定义 Router 内部冲突在 abort 构建中不能由运行时恢复，必须由业务集成测试提前覆盖。
- 运行时 Web 能力句柄属于后续收口目标；当前生产代码只依赖已公开的监听地址、配置视图和应用状态 API。
- 达到本机启动与优雅退出验收不等于完成生产发布，真实配置中心故障、网络分区、依赖超时和强退矩阵仍需逐环境执行。

部署配置与容器信号约束见 [Deployment](deployment.md)。
